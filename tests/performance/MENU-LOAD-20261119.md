# Main menu page-load audit — 2026-11-19

The local anonymous site is fast when the page cache is warm. The clearest data bottleneck is the uncached full-world map response, especially dootronics. Mobile rendering also pays for shared CSS/JavaScript and oversized images. Authenticated requests require substantially more backend work than anonymous page-cache hits.

## Findings and priorities

### 1. Full map responses are large and uncached

Each map request returns all eligible points for its entity type, with no viewport bounds or limit. The measured responses explicitly report `must-revalidate, no-cache, private` and `UNCACHEABLE (no cacheability)` for both page and dynamic cache. Repeated requests therefore keep paying for SQL, JSON serialization and transfer.

| Map | Points | Compressed body kB | Decoded body MB | Median request ms, 3 runs |
| --- | --- | --- | --- | --- |
| dootronic | 56,527 | 500.8 | 3.639 | 646 |
| dootrip | 11,651 | 215.4 | 1.488 | 196 |
| edoovillage | 3,123 | 142.3 | 0.425 | 128 |
| hub | 4,154 | 28.9 | 0.446 | 114 |

The controller uses a direct joined database query and builds the complete array in a loop. The labdooer branch additionally builds an unpaginated Views query and an `IN` list; that branch was inspected but its authorized page was not performance-tested. Source: [MapDataController.php](../../web/modules/custom/labdoo_map/src/Controller/MapDataController.php), [routing](../../web/modules/custom/labdoo_map/labdoo_map.routing.yml).

For dootronics, the desktop browser transferred approximately 501 kB including resource overhead and decoded 3.64 MB. At 390×844 the map begins at y≈948 and no map-data request was made before scrolling; at 1440×1000 it begins at y≈527 and loads immediately. Existing lazy loading and chunked marker creation are working. Sources: [lazy-maps.js](../../web/themes/custom/labdoo_next/js/lazy-maps.js), [labdoo-map.js](../../web/themes/custom/labdoo/js/labdoo-map.js).

**Next work:** evaluate a smaller map representation (server-side clustering or bounded data by viewport/zoom), and add response caching with correct invalidation and variation by permissions, language and filters. Retain access rules and test invalidation; making a response public without that review is not a valid optimization. Measure map-ready time after opening/scrolling separately from LCP.

### 2. First render still downloads shared assets that are mostly unused on each page

**Team activities is the slowest measured mobile route:** median LCP **3.14 s** across four completed observations (2.21–3.16 s), versus **2.31 s** for dootronics across four observations. In the slower activity repetitions, the largest element is the page heading and 85–86% of its simulated LCP is render delay. This is a frontend rendering lead, not evidence of a slow image request. The initial activity trace spends about 683 ms in style/layout; further tracing is needed to attribute individual styles or layout changes.

Lighthouse estimates about **180–300 ms** potential savings from render-blocking resources in the initial route screening. These are model estimates, not measured savings from an implemented change. The header script is tiny; the larger opportunity is the stylesheet chain and per-page asset selection.

On dashboards, about **75 kB** of transferred JavaScript is unused during the measured load: roughly 43 kB from the shared aggregate and 34 kB from Chart.js. Simpler listing pages still report about **39 kB** unused JavaScript. Chart.js itself transfers about 70 kB and expands to approximately 205 kB. Chart/map loaders already defer by viewport; this is an opportunity to reduce bundles and choose chart modules rather than add another generic lazy-loader.

Lighthouse's largest visible element is frequently the shared quotation or cookie banner; on Stories it is the header image. Slow LCP cannot automatically be attributed to the map or database. Sources: [libraries](../../web/themes/custom/labdoo_next/labdoo_next.libraries.yml), [lazy-charts.js](../../web/themes/custom/labdoo_next/js/lazy-charts.js), [theme attachments](../../web/themes/custom/labdoo_next/labdoo_next.theme).

**Next work:** identify styles/scripts required by each route, split optional feature libraries and profile layout before considering critical CSS. Preserve cookie-consent behavior, keyboard navigation and fallback rendering.

### 3. Small UI images download much larger originals

The shared wordmark downloads about **22 kB** at 1200×235 and displays at 120×24. `hub.png` downloads about **61 kB** at 788×642 and displays at 30×24 in the desktop observation. Lighthouse also flags the footer illustration. On simple listing pages, responsive-image opportunities total around **99 KiB**, including below-fold images; these estimates must not all be counted as initial-viewport savings.

**Next work:** provide small image variants with correct dimensions and density-aware sources. This is a focused, comparatively low-risk optimization. Keep the current lazy loading for offscreen icons. Check image cache headers on the actual server: the local router explicitly adds long-lived headers to CSS/JS/JSON/SVG but delegates WebP/PNG to PHP's built-in server, so local image TTL warnings do not establish a production cache defect.

### 4. Cold rendering and authenticated requests need separate backend profiling

Observed anonymous first misses are about **2.1–2.7 s**, versus approximately **4–15 ms** for repeated page-cache hits. Authenticated dynamic-cache hits are around **0.45–0.63 s**; first observed dynamic misses range from roughly **1.25–2.54 s**. Private authenticated responses are expected and must retain their isolation.

The anonymous Actions response initially reports dynamic `UNCACHEABLE (poor cacheability)`, while its anonymous full-page cache still hits. The authenticated probes subsequently show dynamic HIT. This is not evidence that the entire Actions page is always uncacheable.

**Next work:** profile a representative cache miss and authenticated dynamic hit under the intended PHP-FPM/OPcache runtime, separating bootstrap, SQL, Views, blocks and rendering. Review invalidation frequency before choosing a prewarm strategy. No SQL tracing was performed in this audit, so a specific query, missing index or cache backend is not established as the root cause. The observed hit/miss difference alone does not justify adding database indexes.

## Environment defects and coverage limits

- Labdooers returned 403 for anonymous and authenticated basic users. Permission intent was not changed or inferred. Its actual authorized listing and user-map load remain unmeasured.
- Stories emitted missing media-derivative 404s: 23 console entries in its desktop report. The corresponding original media files are absent from this isolated clone. Its score therefore does not certify the page's complete image payload or production behavior. The header image also lacks explicit height.
- Team activities also has non-performance audit failures (accessibility 91/100 and SEO 92/100, including image-alt and link-text issues). Those scores are retained in private summaries; this audit did not fix them.
- Browser probes saw no uncaught JavaScript page exceptions, but this does not erase HTTP asset failures. Lighthouse console audits were reviewed separately.
- No production load, deployment, database repair, cache flush, code optimization, mail delivery or paid-provider call was performed. The maintained 13-minute k6 scenario and full Playwright regression suite were not run: this was a diagnostic navigation audit without an application behavior change. There is no concurrent-capacity or regression-safety claim.
- Test fixture data and missing clone uploads can differ from production. Local scores are not field Core Web Vitals or a production SLA.
